# Формат проекта v3: архив документов

## Цель

Версия 3 добавляет обратимое архивирование папок, сцен и заметок. Архив не является удалением: строки `documents`, тексты, версии и связи остаются в SQLite.

## Схема

В `documents` добавлены:

- `archived_at` — UTC-время архивирования либо `NULL`;
- `archive_root_id` — корень одной атомарной операции архивирования либо `NULL`.

`archive_journal` хранит `command_id`, корневой документ, действие (`archive`/`restore`) и число затронутых строк. Запись состояния, journal и JSON receipt выполняются в одной `BEGIN IMMEDIATE` транзакции.

Инварианты строгой проверки при открытии:

1. `archived_at` и `archive_root_id` либо оба заполнены, либо оба `NULL`;
2. `archive_root_id` указывает на существующий архивный корень, у которого `archive_root_id = id`;
3. активный документ не может иметь архивного родителя;
4. schema SQL, `quick_check`, foreign keys, текущие версии и `project.schema_version` должны точно соответствовать формату.

## Безопасная семантика папки

Архивирование непустой папки одной транзакцией помечает саму папку и всех её **активных** потомков одним `archive_root_id`. Физического удаления нет.

Если потомок был архивирован отдельно раньше, последующая операция над родительской папкой его не перепривязывает. Поэтому:

- восстановление родительской папки не восстанавливает отдельно архивированный потомок;
- отдельно архивированный потомок нельзя восстановить, пока его родитель архивирован;
- после восстановления родителя потомок остаётся отдельной записью в архиве и может быть восстановлен явно.

## Видимость

Обычные `list`, `read`, `save`, `rename`, `duplicate`, checkpoint и FTS search работают только с активными документами. Архивные корни доступны через отдельный paginated `archived` API. Восстановление возвращает весь набор с выбранным `archive_root_id`.

## Идемпотентность

Архивирование и восстановление принимают `command_id` и `expected_revision`.

- повтор того же `command_id` с тем же action/document/revision возвращает сохранённый receipt без новой записи;
- повтор с другим payload или другим action завершается `CommandMismatch`;
- stale `expected_revision` завершается `Conflict`;
- journal и receipt не публикуются при откате транзакции.

## Миграция

Перед v2→v3 создаётся standalone backup через SQLite Backup API:

`backups/pre-migration-v2-<uuid>.alicent-backup`

Backup валидируется как точный v2 до публикации. Только после этого schema-v3 применяется транзакционно. Проект v1 последовательно получает отдельные backup v1 и v2. Повторное открытие v3 не создаёт новых migration backup.
