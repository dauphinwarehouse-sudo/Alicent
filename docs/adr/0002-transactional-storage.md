# ADR 0002 — SQLite как транзакционное документное хранилище v1

Статус: принято для прототипа; full snapshots пересмотреть после benchmark.

Контекст: запись отдельного UTF-8 файла и SQLite metadata не даёт общей атомарной транзакции без дополнительного recovery protocol. Главный приоритет — не потерять рукопись при сбое.

Решение: содержимое каждого документа хранится отдельной SQLite-записью, а не одним общим текстом проекта. FTS5 — external-content индекс. Все изменения текста, истории, журнала и receipt — одна WAL-транзакция с synchronous FULL. Это конкретизация разрешённого ТЗ блочного хранилища, не обещание отдельных Markdown-файлов на диске.

Альтернативы: loose files + journal (сложнее crash recovery), Git (не подходит как единственный транзакционный backend), CRDT сразу (преждевременно для single-user).

Последствия: папку нужно переносить целиком и закрытой; экспорт Markdown необходим позднее. Каждое сохранение сейчас полная версия, плюс receipt дублирует результат: история растёт быстро. До больших проектов нужны delta/snapshot compaction и лимиты retention без потери отката. Текст одного документа целиком загружается в память, проект — нет. Live backup только через SQLite Backup API, не raw copy.
